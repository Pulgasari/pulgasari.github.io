# D3

Ein Werkzeugkasten für datengetriebene Grafiken mit SVG, Canvas und DOM. Von Mike Bostock, seit 2011; hervorgegangen aus der Arbeit mit Jeffrey Heer und Vadim Ogievetsky. Aktuell 7.9.0 (März 2024). D3 ist keine Sammlung fertiger Diagramm-Komponenten, sondern eine Familie separat nutzbarer Module: Skalen, Formen, Layouts, Datenverknüpfung, Interaktion und Animation.

- Website: https://d3js.org
- Repository: https://github.com/d3/d3
- Abhängigkeiten: das Sammelpaket verbindet die einzelnen `d3-*`-Module
- Build: keiner nötig mit Browser-Modulen; ein Bundler kann unbenutzte Exporte entfernen

## Das Problem, das D3 löst

Bei einer individuellen Grafik reichen fertige Balken- oder Linienkomponenten schnell nicht mehr. Dann bleiben viele kleine Probleme: Werte in Pixel übersetzen, Achsen beschriften, Pfade berechnen, Datensätze mit vorhandenen Elementen verbinden und Übergänge animieren.

D3 liefert diese Bausteine, ohne eine eigene Zeichenwelt über den Browser zu legen. Man behält die Kontrolle über SVG und Canvas. Der Preis ist, dass Gestaltung, Beschriftung und Bedienbarkeit weiterhin die Aufgabe der Anwendung sind.

## Kernkonzepte

### 1. Skalen übersetzen Daten

```js
import { scaleLinear } from 'd3';

const x = scaleLinear().domain([0, 100]).range([0, 400]);
x(25);        // 100
x.invert(80); // 20
```

Die Domain ist der Datenraum, die Range der Ausgaberaum. Zeit-, logarithmische und Band-Skalen lösen andere Zuordnungen. Skalen können ohne DOM und ohne D3s Renderer verwendet werden.

### 2. Daten an Elemente binden

```js
import { select, scaleLinear } from 'd3';

const svg = select('#chart').attr('viewBox', '0 0 400 100');
const x = scaleLinear().domain([0, 100]).range([0, 400]);

function update(rows) {
  svg.selectAll('rect')
    .data(rows, row => row.id)
    .join('rect')
    .attr('x', 0)
    .attr('y', (_, index) => index * 25)
    .attr('width', row => x(row.value))
    .attr('height', 20);
}

update([{ id: 'a', value: 25 }, { id: 'b', value: 70 }]);
```

Die Seite enthält `<svg id="chart"></svg>`. `data` verknüpft Datensätze und Knoten, der Schlüssel erhält ihre Identität. `join` erzeugt neue Elemente, behält passende und entfernt entfallene.

### 3. Enter, Update und Exit getrennt behandeln

```js
svg.selectAll('circle').data(points, point => point.id).join(
  enter => enter.append('circle').attr('r', 4),
  update => update,
  exit => exit.remove(),
).attr('cx', point => point.x).attr('cy', point => point.y);
```

Die drei Gruppen erlauben unterschiedliche Übergänge. Das ist ein expliziter Abgleich von Daten und Elementen, kein Vergleich zweier virtueller Bäume.

### 4. Formen und Layouts liefern Geometrie

```js
import { line } from 'd3';

const path = line().x(point => point.x).y(point => point.y);
path([{ x: 0, y: 20 }, { x: 100, y: 50 }]); // svg path data
```

Formgeneratoren liefern Pfade; Force-, Hierarchie- und Geo-Module berechnen Positionen oder Projektionen. Diese Ergebnisse lassen sich auch von [Preact](preact.md), rat oder Canvas zeichnen lassen.

### 5. Interaktion und Übergänge

`d3-zoom`, `d3-drag` und `d3-brush` beschreiben typische Gesten. `selection.transition()` interpoliert Attribute über die Zeit. Bei einer eingebetteten Grafik muss geklärt sein, ob D3 oder das umgebende Framework diese Attribute schreibt.

## Wie es intern arbeitet

Eine Selection enthält Gruppen von DOM-Knoten und deren Eltern. Gebundene Daten liegen am jeweiligen Knoten als `__data__`. Beim Join ordnet D3 neue Daten vorhandenen Knoten nach Index oder Schlüssel zu; daraus entstehen Enter-, Update- und Exit-Gruppen.

Aufrufe wie `attr` schreiben direkt ins DOM. Rechenmodule arbeiten dagegen unabhängig davon: Eine Skala bildet Werte ab, ein Formgenerator erzeugt Geometrie. D3 beobachtet keine Datenmutation automatisch. Die Anwendung entscheidet, wann sie `update` aufruft.

## Stärken und Schwächen

- **Stark:** freie Gestaltung, einzeln nutzbare Module, guter Zugriff auf Web-Standards, kontrollierbare Übergänge und Identität. Reine Rechenmodule passen in praktisch jedes UI-Modell.
- **Schwach:** selbst einfache Diagramme verlangen viele Entscheidungen. Responsivität, Barrierefreiheit und Datenfehler sind nicht automatisch erledigt. Zwei Systeme, die denselben DOM-Teilbaum verwalten, können sich gegenseitig überschreiben.

## Für rat und aufbau

- **Datenmodule zuerst:** Skalen, Pfade und Layouts könnten als reine Berechnungen in rats Computeds laufen (Vorschlag). Das Markup und seine Bindungen blieben bei rat.
- **Ein Eigentümer pro Teilbaum:** Wenn D3 selbst rendert, sollte eine Behavior ihm einen abgegrenzten SVG- oder Canvas-Bereich geben und beim Abbau Listener und Animationen beenden.
- **Keys lösen dasselbe Identitätsproblem** wie rats keyed `@for`; D3 macht Enter und Exit zusätzlich als eigene Phasen sichtbar. Das wäre ein nützlicher Vergleich für Listenanimationen.
- **Keine neue Chart-Runtime aus Gewohnheit:** Für aufbau ist D3 ein Vorrat an Algorithmen. Ein vollständiger D3-Import wäre für eine einzelne Skala unnötig.
