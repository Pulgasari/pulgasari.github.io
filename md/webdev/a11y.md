# Barrierefreiheit (a11y) im Webdev

Ein Überblick: wer betroffen ist, wie die Hilfsmittel funktionieren, was man baut, was zu wenig bekannt ist und wie man testet. Am Ende die Anknüpfungspunkte in aufbau und zugriff.

## 1. Um wen es geht

Etwa jeder sechste Mensch lebt mit einer Behinderung (WHO: rund 1,3 Milliarden). Dazu kommen viele, die es nur vorübergehend oder in einer Situation betrifft.

| Bereich | Beispiele | Was sie brauchen |
|---|---|---|
| **Sehen** | blind, sehbehindert, Farbfehlsichtigkeit (etwa 8 % der Männer), Blendempfindlichkeit | Screenreader, Vergrößerung, Kontrast, Farbe nicht als einzige Information |
| **Hören** | gehörlos, schwerhörig | Untertitel, Transkripte, visuelle statt akustischer Signale |
| **Motorik** | Lähmung, Tremor, nur eine Hand, Muskelschwäche, RSI | Tastatur, Schalter, Sprachsteuerung, große Klickflächen, keine Präzisionsgesten |
| **Kognition, Neurologie** | ADHS, Legasthenie, Autismus, Demenz, Hirnverletzung, Lernbehinderung | klare Sprache, Konsistenz, keine Zeitlimits, Fehlertoleranz, wenig Ablenkung |
| **Anfälle, Gleichgewicht** | photosensitive Epilepsie, Schwindel bei Bewegung (vestibulär) | keine Blitze, reduzierte Bewegung |
| **Situativ, vorübergehend** | Arm gebrochen, grelles Sonnenlicht, Baby im Arm, laute Umgebung, müde, fremde Sprache | dasselbe wie oben |

Der **Curb-Cut-Effekt**: Die abgesenkte Bordsteinkante war für Rollstühle gedacht und hilft allen mit Kinderwagen, Koffer oder Fahrrad. Untertitel, Kontrast, Tastaturkürzel und klare Sprache nutzen ebenfalls fast allen.

## 2. Wie die Hilfsmittel funktionieren

### Der Accessibility Tree: die zentrale Idee

Screenreader & Co. lesen **nicht den DOM**. Der Browser baut aus DOM, CSS und ARIA einen zweiten Baum, den **Accessibility Tree**. Jeder Knoten darin hat:

- **Rolle:** button, link, heading (Ebene 2), textbox, list …
- **Name:** „Speichern“, das, was vorgelesen wird
- **Zustand:** checked, expanded, disabled, pressed, selected, invalid …
- **Wert:** z. B. der Text in einem Feld oder 40 % bei einem Slider
- **Beziehungen:** beschrieben durch, steuert, Teil von …

Diesen Baum reicht der Browser über die **Accessibility-Schnittstelle des Betriebssystems** weiter:

| System | Schnittstelle |
|---|---|
| Windows | UI Automation (UIA), früher MSAA/IA2 |
| macOS / iOS | NSAccessibility / UIAccessibility |
| Linux | AT-SPI |
| Android | AccessibilityNodeInfo, gelesen von einem AccessibilityService |

Das Hilfsmittel spricht nur mit dieser Schnittstelle. Deshalb ist **semantisches HTML** so wichtig: Ein `<button>` landet mit Rolle, Namen und Zustand automatisch dort, ein `<div onclick>` als bloße Gruppe ohne alles.

Zu sehen in Chrome DevTools: Elements → Accessibility (auch als ganzer Baum), in Firefox: Accessibility Inspector.

### Und native Apps, z. B. Android?

Genau dasselbe Prinzip, nur ohne DOM:

- **Native Android (Views):** Jede View meldet Rolle, Text und `contentDescription` an das Accessibility-Framework. TalkBack ist ein AccessibilityService, der diesen Baum liest.
- **Jetpack Compose:** Hat einen eigenen **Semantics Tree**, `Modifier.semantics { … }` entspricht ungefähr ARIA.
- **iOS:** UIAccessibility (`accessibilityLabel`, `accessibilityTraits`), in SwiftUI Modifier wie `.accessibilityLabel()`.
- **WebView / Capacitor / Cordova / PWA:** Die WebView **übersetzt den Accessibility Tree des HTML** in den nativen Baum. Gutes HTML ist also auch in der Capacitor-App von zugriff für TalkBack zugänglich, schlechtes genauso wenig wie im Browser.
- **Canvas, WebGL, Spiele-Engines:** ein schwarzes Loch. Dort gibt es keinen Baum, außer man baut ihn selbst (Fallback-DOM, ARIA, oder bei Flutter dessen Semantics).

### Wie eine blinde Person eine Website nutzt

- **Sie liest nicht von oben nach unten**, sondern springt über die Struktur:
  - `H` nächste Überschrift, `1`–`6` nach Ebene
  - `D`/`R` Landmarks (main, nav, header …)
  - `K` Links, `F` Formularfelder, `T` Tabellen, `L` Listen
  - Listen aller Überschriften oder Links (NVDA: Insert+F7)
- **Oft sehr schnell:** 300 bis 500 Wörter pro Minute sind unter Geübten normal.
- **Zwei Modi:**
  - Lesemodus (Browse): Pfeiltasten gehen durch den Inhalt.
  - Fokusmodus: Tasten gehen an das Formularfeld.
  - Widgets mit falscher Rolle bringen die Umschaltung durcheinander.
- **Ein Seitenaufbau ohne Überschriften** ist wie ein Buch ohne Inhaltsverzeichnis und Kapitel.

### Wie Screenreader auf dem Handy funktionieren (TalkBack, VoiceOver)

- **Wischen** rechts/links: nächstes bzw. vorheriges Element. **Doppeltippen**: das fokussierte Element aktivieren.
- **Explore by touch:** Den Finger über den Bildschirm ziehen, vorgelesen wird, was darunter liegt.
- **Rotor** (iOS) bzw. Lesesteuerung (Android): wählen, ob das Wischen nach Überschriften, Links, Wörtern usw. springt.
- **Eigene Gesten der App** (Wischen zum Löschen, Pinch, Long Press) werden vom Screenreader abgefangen. Sie brauchen eine Alternative: einen sichtbaren Button, ein Menü oder benannte Aktionen am Element (Android: AccessibilityAction, iOS: `accessibilityCustomActions`).
- **Der Anteil ist hoch:** Nach WebAIM-Umfragen nutzen die meisten Screenreader-Nutzer auch mobil einen, und dort überwiegend VoiceOver auf dem iPhone (rund 70 %).

### Die Screenreader

| | System | |
|---|---|---|
| **NVDA** | Windows | gratis, Open Source, sehr verbreitet |
| **JAWS** | Windows | kommerziell, lange Marktführer |
| **Narrator** | Windows | eingebaut |
| **VoiceOver** | macOS, iOS | eingebaut |
| **TalkBack** | Android | eingebaut |
| **Orca** | Linux | |

Dazu **Braillezeilen**: Sie zeigen den Text als Punktschrift an, oft gleichzeitig mit der Sprachausgabe.

### Weitere Hilfsmittel, die oft vergessen werden

- **Vergrößerung:** OS-Lupe, Browser-Zoom bis 400 %, ZoomText. Das nutzen deutlich **mehr Menschen als Screenreader**.
- **Schriftgröße des Systems:** Android Font Scale, iOS Dynamic Type. Browser-Schriftgröße in `rem` respektieren.
- **Hochkontrast bzw. Forced Colors (Windows):** Das System ersetzt alle Farben durch wenige Systemfarben. Hintergrundbilder, `box-shadow` als Rahmen und farbige Zustände verschwinden.
- **Invertierte Farben, Graustufen, Farbfilter:** Die bietet das Betriebssystem an.
- **Nur Tastatur:** Tab, Shift+Tab, Enter, Leertaste, Pfeiltasten, Escape.
- **Schaltersteuerung (Switch Access):** ein oder zwei Knöpfe, das System springt nacheinander durch alle bedienbaren Elemente.
- **Sprachsteuerung:** Voice Control (Apple), Voice Access (Android), Dragon. Man sagt z. B. „tippe Speichern“ und zielt dabei auf den **sichtbaren** Text.
- **Augensteuerung, Kopfmaus, Mundsteuerung (Sip-and-puff):** Zeigen ist langsam und ungenau, große Ziele helfen.
- **Vorlesen für Sehende:** Select to Speak, Reader-Modus. Hilft bei Legasthenie.
- **Untertitel, Transkripte, Gebärdensprache** bei Video und Audio.

## 3. Regeln und Recht

- **WCAG 2.2** (Web Content Accessibility Guidelines, W3C, seit Oktober 2023) ist der Maßstab.
  - Vier Prinzipien, „POUR“: **wahrnehmbar, bedienbar, verständlich, robust**.
  - Stufen A, AA, AAA. Gefordert ist in der Regel **AA**.
- **EN 301 549** ist die europäische Norm dazu, sie verweist auf die WCAG und gilt auch für Apps und Dokumente.
- **European Accessibility Act, in Deutschland das BFSG (Barrierefreiheitsstärkungsgesetz), gilt seit dem 28.06.2025.**
  - Betroffen sind viele Produkte und Dienstleistungen für Verbraucher: Onlineshops, Banking, E-Books, Personenverkehr, Telekommunikation, jeweils mit ihren Websites und Apps.
  - Ausgenommen sind Kleinstunternehmen mit Dienstleistungen (unter 10 Beschäftigte und höchstens 2 Mio. € Umsatz).
- **BITV 2.0** gilt für öffentliche Stellen in Deutschland.
- **ARIA** (WAI-ARIA) ist die Ergänzung, wenn HTML allein nicht reicht: Rollen, Zustände und Eigenschaften für eigene Widgets.
  - Die **ARIA Authoring Practices (APG)** zeigen die Muster: Tabs, Dialog, Combobox, Menü, Akkordeon …

## 4. Was man beim Bauen beachtet

### Struktur und Semantik

- **Erst HTML, dann ARIA.** Die erste Regel von ARIA lautet: Keine ARIA ist besser als falsche ARIA. Ein `<button>` bringt Rolle, Fokus, Enter/Leertaste und Formularverhalten mit, `<div role="button">` nichts davon außer der Rolle.
- **Landmarks:** `header`, `nav`, `main` (einmal), `aside`, `footer`, `search`, `form` mit Namen.
- **Überschriften als echte Gliederung:** eine `h1`, dann ohne Sprünge. Überschriften nach Struktur wählen, nicht nach Größe.
- **Listen als `ul`/`ol`, Tabellen mit `th`, `scope` und `caption`.** Keine Tabellen fürs Layout.
- **`lang` am `<html>`**, und an fremdsprachigen Passagen. Der Screenreader wählt danach Stimme und Aussprache. Falsches `lang` heißt deutscher Text mit englischer Aussprache.
- **Link oder Button:** Ein Link führt woanders hin, ein Button tut etwas.

### Namen

- **Jedes Bedienelement braucht einen zugänglichen Namen:** über sichtbaren Text, `<label>`, `aria-labelledby` oder `aria-label`.
- **Icon-Buttons** brauchen `aria-label` (oder unsichtbaren Text). `title` reicht nicht: Auf Touch und Tastatur taucht es nicht auf.
- **Bilder:**
  - `alt` beschreibt, was das Bild in diesem Zusammenhang **bedeutet**, nicht jedes Pixel.
  - Dekorative Bilder bekommen `alt=""`, dann werden sie übersprungen.
  - Fehlt `alt` ganz, liest mancher Screenreader den Dateinamen vor.
- **Linktexte müssen allein verständlich sein.** In der Linkliste steht „hier klicken“ zehnmal hintereinander.
- **Label in Name (WCAG 2.5.3):** Der zugängliche Name muss den sichtbaren Text enthalten. Steht auf dem Button „Senden“ und im `aria-label` „Formular abschicken“, funktioniert „tippe Senden“ in der Sprachsteuerung nicht.

### Tastatur und Fokus

- **Alles, was mit der Maus geht, geht mit der Tastatur.**
- **Den Fokus immer sichtbar lassen:** `:focus-visible` mit deutlichem Ring (mindestens 3:1 Kontrast). Nie `outline: none` ohne Ersatz.
- **Reihenfolge = DOM-Reihenfolge.** Kein positives `tabindex`. `tabindex="-1"` nur für per Skript fokussierte Elemente.
- **Fokus-Management:**
  - Dialog öffnen: Der Fokus geht hinein und bleibt drin (Focus Trap). Beim Schließen kehrt er zum Auslöser zurück. `<dialog>` mit `showModal()` macht das von selbst.
  - Hintergrund per `inert` sperren.
  - **In SPAs die Navigation ansagen:** `document.title` ändern und den Fokus auf die neue Überschrift setzen oder eine Live-Region nutzen. Sonst merkt ein Screenreader-Nutzer nicht, dass sich die „Seite“ geändert hat.
- **Skip-Link** („Zum Inhalt springen“) als erstes fokussierbares Element.
- **Roving tabindex** in Gruppen (Toolbar, Tabs, Radiogruppe): ein Tab-Stopp für die Gruppe, darin Pfeiltasten.

### Zustände und Änderungen

- **Zustände in ARIA spiegeln:** `aria-expanded`, `aria-pressed`, `aria-selected`, `aria-current="page"`, `aria-invalid`, `aria-busy`.
- **Live-Regionen** für Dinge, die ohne Fokuswechsel passieren: Toasts, „3 Ergebnisse“, „gespeichert“, Ladezustände.
  - `role="status"` (höflich) oder `role="alert"` (unterbricht), bzw. `aria-live`.
  - Die Region muss **schon vorher** im DOM stehen. Erst der Inhalt wird eingesetzt.

### Formulare

- **Jedes Feld mit echtem `<label>`.** Ein Placeholder ist **kein** Label: Er verschwindet beim Tippen und hat zu wenig Kontrast.
- **Fehler:** als Text, am Feld (`aria-describedby`, `aria-invalid="true"`), nicht nur rot. Beim Absenden Fokus auf den ersten Fehler oder auf eine Fehlerübersicht.
- **`autocomplete`-Attribute** (`email`, `name`, `street-address`, `one-time-code` …). Das hilft enorm bei motorischen und kognitiven Einschränkungen und ist WCAG 1.3.5.
- **Zusammengehörige Felder** in `fieldset` + `legend` (Radiogruppen!).
- **Nichts doppelt abfragen** (WCAG 3.3.7), was schon eingegeben wurde.
- **Barrierearme Anmeldung (WCAG 3.3.8):** keine kognitiven Tests. Einfügen in Passwortfelder erlauben, Passwortmanager und Passkeys unterstützen. Rätsel-CAPTCHAs sind ein großes Problem.

### Sehen: Farbe, Kontrast, Größe

- **Kontrast (AA):**
  - Text 4,5:1
  - großer Text (ab 24px bzw. 18,66px fett) 3:1
  - Bedienelemente, Rahmen, Fokusring und Icons 3:1 (WCAG 1.4.11)
- **Farbe nie als einzige Information.** Rot/grün für Fehler/Erfolg zusätzlich mit Icon oder Text, Links im Fließtext zusätzlich unterstrichen.
- **Zoom bis 400 % ohne horizontales Scrollen** (Reflow, 320 CSS-px Breite). Schrift in `rem`, `user-scalable=no` nie setzen.
- **Textabstände (WCAG 1.4.12):** Nutzer überschreiben Zeilenhöhe, Buchstaben- und Wortabstand, das Layout darf dabei nicht brechen (keine festen Höhen um Text).
- **OS-Einstellungen respektieren:**
  - `prefers-color-scheme`
  - `prefers-contrast: more`
  - `forced-colors: active` (dann mit Systemfarben wie `CanvasText`, `ButtonText`, `Highlight` nachbessern)
  - `prefers-reduced-transparency`

### Bewegung und Zeit

- **`prefers-reduced-motion`:** große Bewegungen, Parallax, Zoom-Übergänge und Autoplay reduzieren. Eine Überblendung ist meist noch in Ordnung.
- **Nichts blitzt öfter als dreimal pro Sekunde** (Epilepsie, WCAG 2.3.1).
- **Bewegtes, das länger als 5 Sekunden läuft** (Karussell, Autoplay-Video, animierter Hintergrund), braucht Pause/Stopp.
- **Zeitlimits:** warnen, verlängern lassen, oder ganz weglassen.

### Zeiger und Touch

- **Zielgröße mindestens 24×24 CSS-px (WCAG 2.5.8, AA).** Empfohlen sind 44×44 (Apple) bzw. 48×48 dp (Android).
- **Mehrfinger- oder Pfadgesten** (Pinch, Wischen) brauchen eine Einzeltipp-Alternative (2.5.1).
- **Ziehen** (Drag-and-drop, Slider ziehen) braucht eine Alternative ohne Ziehen (2.5.7, neu in 2.2).
- **Auslösen beim Loslassen**, nicht beim Drücken: Dann kann man abbrechen, indem man wegrutscht (2.5.2).
- **Schütteln zum Rückgängig** und andere Bewegungssteuerung: abschaltbar und mit Alternative (2.5.4).

### Hover und Popups

- **Inhalte, die bei Hover oder Fokus erscheinen** (Tooltips, Menüs), müssen (WCAG 1.4.13):
  - sich mit Escape schließen lassen,
  - selbst überfahrbar sein, ohne zu verschwinden,
  - so lange bleiben, bis man weggeht.
- **Nur bei Hover** gibt es auf Touch gar nichts. Wichtige Infos nie nur im Tooltip.

### Verstehen (kognitiv)

- **Klare, kurze Sprache.** Einfache Sprache für alle, Leichte Sprache als eigenes Angebot.
- **Konsistenz:** Navigation, Namen und Hilfe immer am selben Ort (3.2.3, 3.2.6).
- **Fehler vermeiden:** bestätigen, rückgängig machen, prüfen vor dem Absenden.
- **Wenig Ablenkung:** keine Popups mitten im Tun, keine Dark Patterns.
- **Legasthenie:** Zeilenlänge etwa 60 bis 80 Zeichen, großzügiger Zeilenabstand, linksbündig statt Blocksatz. Spezielle Legasthenie-Schriften sind in Studien kaum wirksamer als eine gute serifenlose Schrift.

### Medien

- Untertitel für Videos (`<track kind="captions">`) und Transkripte für Audio und Podcasts.
- Audiodeskription, wenn wichtige Information nur im Bild steckt.
- Kein Autoplay mit Ton.

### Web Components und Shadow DOM

- **Rolle und Zustände über `ElementInternals`** (`internals.role`, `ariaChecked` …) setzen, nicht über sichtbare Attribute am Host, die ein Autor überschreiben könnte.
- **Formularverhalten:** `static formAssociated = true` bringt Label-Zuordnung, Validierung und Reset.
- **ARIA-Bezüge über Shadow-Grenzen hinweg gehen (noch) nicht.** `aria-labelledby`, `aria-controls` und `aria-activedescendant` finden keine IDs in einem anderen Root. Der Vorschlag „Reference Target“ soll das lösen. Bis dahin müssen Bezüge im selben Root liegen.
- **`delegatesFocus`** für Hosts, die ihren Fokus an ein inneres Element geben.

## 5. Was zu wenig bekannt ist

- **Mehr Menschen nutzen Zoom und große Schrift als Screenreader.** Reflow und `rem` sind oft wichtiger als ARIA.
- **Blinde Menschen nutzen vor allem Smartphones,** meist das iPhone. Mobile Screenreader-Tests sind Pflicht, nicht Kür.
- **Accessibility-Overlays** (Widgets à la accessiBe, UserWay) beheben die Probleme nicht, stören Hilfsmittel oft sogar und haben Klagen nicht verhindert. Viele Betroffene lehnen sie ab. Sie ersetzen keine barrierefreie Umsetzung.
- **Eigene Einstellungs-Widgets** (Kontrast, Entsättigen, Schrift größer) sind nett, aber das Betriebssystem bietet das meist schon, systemweit und gewohnt.
  - Wichtiger ist, dass die Seite diese Einstellungen **respektiert** (`prefers-*`, Forced Colors, Schriftgröße, Zoom).
  - Eigene Optionen lohnen sich dort, wo das OS nichts hat: Animationen der App, Lesemodus, Zeilenabstand, Schrift. Dann aber gespeichert.
- **`aria-label` ersetzt den sichtbaren Text.** Weicht er ab, scheitert die Sprachsteuerung (siehe Label in Name).
- **`display: none` und `visibility: hidden` verstecken auch vor Screenreadern.** Für Text nur für Screenreader gibt es eine „visually-hidden“-Klasse (clip + 1px), für das Gegenteil `aria-hidden="true"`.
- **`display: contents` nimmt Elementen ihre Box** und damit Fokus und bei manchen Rollen die Semantik.
- **Safari/VoiceOver entfernt die Listen-Rolle bei `list-style: none`.** Wenn die Rolle zählt, `role="list"` dazuschreiben.
- **CSS-`content` wird vorgelesen.** Icon-Fonts und Sternchen in `::before` landen in der Sprachausgabe. Es gibt eine Syntax mit Alternativtext: `content: "★" / ""`.
- **Emojis werden mit vollem Namen vorgelesen,** „Fancy Unicode“ (𝓯𝓪𝓷𝓬𝔂, 𝐛𝐨𝐥𝐝) wird buchstabiert oder gar nicht gelesen.
- **Das `title`-Attribut** ist für Tastatur und Touch praktisch unsichtbar.
- **Placeholder als Label** hat zu wenig Kontrast und verschwindet beim Tippen.
- **„Öffnet in neuem Tab“ ohne Hinweis** verwirrt, weil der Zurück-Knopf dann nicht funktioniert.
- **Automatische Tests finden nur etwa 30 bis 40 %** der Probleme. Den Rest findet man nur manuell.
- **Barrierefreiheit ist kein Zusatz, der am Ende draufkommt.** Nachträglich kostet sie ein Vielfaches.
- **Kognitive Barrierefreiheit** ist der am meisten vernachlässigte Bereich, weil sie sich schlecht automatisch prüfen lässt.

## 6. Testen

- **Automatisch:**
  - axe (DevTools-Erweiterung, `axe-core` in Playwright), Lighthouse, WAVE
  - eslint-plugin-jsx-a11y bzw. Linter für Templates
  - Kontraste von Paletten per Skript prüfen
- **Manuell, in dieser Reihenfolge lohnend:**
  1. **Nur mit der Tastatur** durch alles: Kommt man überall hin und wieder heraus? Sieht man immer, wo der Fokus ist?
  2. **Zoom 200 und 400 %** sowie ein schmales Fenster (320px).
  3. **Screenreader:** NVDA + Firefox/Chrome (Windows), VoiceOver + Safari (Mac/iPhone), TalkBack + Chrome (Android).
  4. **DevTools → Rendering:** Forced Colors, `prefers-reduced-motion`, Sehschwächen emulieren (Farbfehlsichtigkeit, Unschärfe).
  5. **Accessibility Tree** in den DevTools: Hat jedes Element eine Rolle und einen Namen?
- **Android-Tools:** Accessibility Scanner (App von Google), TalkBack, Switch Access, Voice Access.
- **Am besten: echte Nutzerinnen und Nutzer testen lassen.**

## 7. Anknüpfungspunkte in aufbau und zugriff

Schon da:
- **aufbau-elements** setzen Rollen und Zustände über `ElementInternals` und sind echte Formularelemente (`formAssociated`).
- **`--motion` und `prefers-reduced-motion`** in animate. `app-view` wechselt ohne Animation, wenn weniger Bewegung gewünscht ist.
- **`aufbau-embed`:** Der Platzhalter ist ein Button mit Namen.
- **Das Dock von zugriff** setzt `aria-current="page"`.
- **Capacitor:** Die WebView reicht den Accessibility Tree an TalkBack weiter. Gutes HTML trägt also bis in die Android-App.

Lohnenswert (nur notiert, nichts davon umgesetzt):
- **`app-view`:** Beim Wechsel die Navigation ansagen, also Fokus auf die Überschrift der neuen View oder eine Live-Region, dazu `document.title`.
- **Forced Colors:** Die Markierung des aktiven Dock-Elements ist ein `box-shadow` und verschwindet im Hochkontrast. Auch der Skin sollte einmal unter `forced-colors: active` angesehen werden.
- **Paletten:** automatischer Kontrasttest `--color-fg` gegen `--color-bg` und `--color-ink` gegen `--color-bg`, z. B. als Skript beim Build.
- **Icon-only-Buttons in zugriff:** Viele haben nur `title`. Sie bräuchten `aria-label`.
- **`aufbau-toast`:** als Live-Region (`role="status"` bzw. `alert` bei Fehlern) prüfen.
- **Shadow DOM:** ARIA-Bezüge (`aria-controls`, `aria-activedescendant`) nur innerhalb desselben Roots nutzen, z. B. im Picker.
- **Zielgrößen:** kleine Icon-Buttons auf mindestens 24px, besser 44px prüfen.
- **`lang`:** Apps mit Inhalten in anderen Sprachen (Podcasts, Feeds) könnten `lang` am Inhalt setzen, wenn die Quelle es angibt.
